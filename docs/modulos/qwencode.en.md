# Qwen Code (Alibaba) — module sheet (`qwencode`)

> Anything marked "Verified in code" was read in the cited code (file:line); "Inference" = not verified on a device. Nothing was tested on a device.
> Shared document of the family: `docs/modulos/cli-tools.md`. Where they differ, `CliToolFragment.kt` takes precedence.

## 1. What it is and what it is for
Alibaba's coding CLI (a Gemini CLI fork) on top of Qwen3-Coder, npm package `@qwen-code/qwen-code`, command `qwen` (`qwencode.sh:3-15`). The module installs the CLI; the API key/login is configured inside the session with `/auth` (the `qwen auth` subcommand was removed upstream, comment `CliToolFragment.kt:231-233`).

## 2. Classification
**ADD-ON / EXTENSION (the richest of the family: approval mode, Engram and local provider)**

Rationale (verified in code): no service or state of its own; the actions open a terminal. It is the CLI with the most controls of its own (5-value approval mode, Engram MCP connection), but each one is a terminal command. The real native function is writing `~/.qwen/.env` for the local provider (`LocalCliProviderNative.kt:25-35`).

UI options (approx.): **~12** (5 common + Login (hint) + Send prompt + Continue + Approval mode + Connect Engram + Use Ollama + Use llama-server).

## 3. Installation (`modulos/qwencode.sh`)
- Flags: `--silent`, `--force`, `--describe`, `--describe-files` (`qwencode.sh:42-50`). Version 1.0.0.
- STEP 1 Node.js (`nodejs-lts` if missing, `:124-140`); STEP 2 `npm install -g @qwen-code/qwen-code@latest` (`:142-157`) + `fix_npm_shebang_wrapper qwen` (rewrites the npm symlink as a bash wrapper with an absolute shebang, `lib.sh:560`) + `verify_binary_installed qwen` (`qwen --version`); STEP 3 API key skipped in silent mode (only a `warn`, `:159-169`).
- Registry: `installed, version, channel=npm, install_date` (`:175-179`). Package has no version pin (`@latest`) and no hash verification.
- `modules.json`: `installMethods: ["npm"]`, `requires: ["nodejs"]`, ~60MB.
- `--describe-files` packages the wrapper and `$(npm root -g)/@qwen-code/**` (`:53-75`).

## 4. Execution
- Command: `qwen` (`terminalCommand` in `modules.json`; `baseCommand` in `CLI_MODULE_CONFIGS`, `CliToolFragment.kt:239-250`).
- Fragment: `CliToolFragment` (`app/src/main/java/com/termux/app/ui/CliToolFragment.kt`, routed from `ModuleDetailNavigator.kt:57`).
All UI actions end in `launchCliTerminalCommand()` (`CliToolFragment.kt:451-454`) -> `BaseModuleFragment.launchTerminalCommand()` (`BaseModuleFragment.kt:994`) -> `TermuxActivity.openTerminalWithCommand(cmd, sessionName = module name)`. In other words: the app does **not** run the CLI through `ProcessBuilder` or capture its output; it opens a real terminal session and types the command. There is no background service, no port (`port: ""`), and no on/off switch (`hasSwitch: false`) in `modules.json`. The "installed" state is detected by the binary being in PATH (`ModuleInstalled.kt`, `LiveCheck.PATH_BINARY`).
- `needsGlibcCompat` = false: `LD_PRELOAD` is kept (needed by the npm shim).

## 5. UI functions and options
Controls common to all CLIs in `CliToolFragment` (`CliToolFragment.kt:466-620`):
- STATUS card (`:472-476`): id, version read from the registry (`<id>.version`, `:622-628`) and base command. Read-only.
- USE card (`:478-497`): **Open in terminal** (`promptOpenLocation` -> default command or `cd '<folder>' && qwen`) and **Manage projects** (`showProjectsMenu`, launches `cd '<project>' && qwen`).
- MAINTENANCE card (`:604-619`): **Update** (`updateModuleService`), **Diagnose** (`runModuleDoctorForThis`) and **Uninstall** (dialog with a "deep uninstall" checkbox, `confirmUninstall` `:863-897`).

Controls specific to this module (`CliToolFragment.kt:239-250`):
- **Log in**: no `authCommand`; shows the toast `clitool_cfg_authhint_qwencode` and opens `qwen` so the user runs `/auth` (`runAuth`, `:630-638`).
- **Send prompt**: `qwen --prompt '<prompt>'` (`:244`).
- **Continue last session**: `qwen --continue` (with a folder dialog, `:246`).
- **Approval mode**: dialog with `plan / default / auto-edit / auto / yolo`; immediately launches `qwen --approval-mode=<mode>` (`:247-248`, `showApprovalModeDialog` `:746-755`).
- **Connect Engram** (MORE OPTIONS): `qwen mcp add engram engram mcp --transport stdio` (`:249`).
- **Use local Ollama / llama-server**: upsert of `OPENAI_API_KEY=local`, `OPENAI_BASE_URL`, `OPENAI_MODEL` in `~/.qwen/.env` (`LocalCliProviderNative.kt:25-35`).

## 6. Files and paths it creates
- Global npm package `@qwen-code/qwen-code` (in `npm root -g`) and wrapper `$PREFIX/bin/qwen` (bash, generated by `fix_npm_shebang_wrapper`).
- `~/.qwen/` (the CLI's own config) and `~/.qwen/.env` (written by the UI for the local provider).
- `~/.install_qwencode_checkpoint` (deleted at the end). Registry: `qwencode.*`.

## 7. Security
- The **yolo** approval-mode option is launched with no additional confirmation (`showApprovalModeDialog` runs as soon as the item is tapped, `:750-752`); the CLI gets full autonomy over the session's project.
- `OPENAI_API_KEY=local` is a literal, not a secret. The real Qwen API key is entered by the user inside the session (the app does not store it).
- npm `@latest` with no hash. Prompt escaped with `shellEscape`.
- No `curl | bash`.

## 8. Issues and limitations found
- The **Connect Engram** button does not check that the `engram` module is installed; `requires` only lists `nodejs` (`modules.json`). If it is missing, the command fails in the terminal with no explanation in the UI.
- `deepUninstallPlan` only runs `npm uninstall -g @qwen-code/qwen-code` (`ModuleController.kt:886-889`); it leaves `~/.qwen` (including the local-provider `.env`).
- The approval mode is not persisted: each selection opens a new session with the flag; there is no state or indicator of the active mode.
- `configureQwenCode` upserts by key (it does not overwrite the rest of `.env`), but a previous user `OPENAI_BASE_URL` is overwritten.
- Inference: login depends on the user knowing `/auth`; the hint is an ephemeral toast.
