# Desktop environments inside proot distributions

Kairos can boot a full desktop environment (XFCE4, LXQt, or MATE) inside a Linux distribution
installed via `proot-distro`, rendering on the same embedded X11 server used by the native
desktop mode. This document describes the mechanism, the state of the app catalog available
inside a distro, and a set of concrete improvements identified through research into similar
projects in the Termux/Android ecosystem.

## Mechanism

Installing the desktop environment inside the distro runs the appropriate package manager
(`apt`, `dnf`, `pacman`, or `apk` depending on the distribution) inside a `proot-distro login`
session, followed by a real functional check (that the desktop session binary actually exists
and is executable, not just that the install command exited without error). Starting the
graphical session uses `dbus-launch --exit-with-session` together with the chosen desktop
environment, with `DISPLAY` pointing at the same embedded X11 server used by the rest of the
app — never a separate server.

Patterns already adopted from reference projects in the ecosystem (`sabamdarif/termux-desktop`,
`orailnoor/DroidDesk`, `vee63b/RDeX`): keeping the session awake with a wake lock while the
desktop is active, an explicit software-rendering fallback when no GPU acceleration is
available, cleanup of stale runtime directories before starting the audio server, and automatic
generation of `.desktop` launchers both for Kairos's own command-line tools and for applications
installed inside the distro.

## App selection inside a distro

The current curated catalog covers web browsing, office productivity, image/vector editing,
video/audio, and file transfer, plus a free-text field to install any package available in the
distro's repositories. Categories identified as real gaps, with their apt package equivalent on
Debian/Ubuntu arm64:

| Category | apt package | Rationale |
|---|---|---|
| Lightweight graphical IDE/editor | `geany` | A viable option in a rootless ARM64 container — VS Code/VSCodium don't publish an official apt repo for arm64 without adding third-party repositories. |
| Document/PDF viewer | `evince` | Today, opening a PDF forces opening the entire office suite. |
| Password manager | `keepassxc` | Fits Kairos's use as a personal homelab — no app covers this category today. |
| Remote client (RDP/VNC/SSH GUI) | `remmina` | Lets the desktop inside the distro connect out to other machines on the network, complementing Kairos's own VNC viewer. |
| Audio editor | `audacity` | Complements the already-available content-creation tools (OBS, Blender). |
| Archive manager | `xarchiver` | A basic desktop utility that's missing today — opening a `.zip`/`.tar.gz` currently requires a terminal. |

## Wallpaper: the real mechanism per desktop environment

Setting the wallpaper inside a `proot` container without a full D-Bus session bus is a known
source of silent failures across the whole ecosystem. The correct mechanism depends on the
desktop environment:

- **XFCE4** uses `xfconf-query`, which requires a valid `DBUS_SESSION_BUS_ADDRESS` pointing to a
  real socket — many distros compile D-Bus with X11 autolaunch disabled for security, so an
  isolated command run outside the active session fails with a connection error. The correct
  approach is to run the command **inside** the same process/session that already has that value
  exported (the active graphical session), rather than as a new, isolated command. The exact
  property path (`/backdrop/screen0/monitorX/workspaceN/last-image`) depends on the actual
  monitor name exposed by the X11 server, and should be discovered with `xfconf-query -c
  xfce4-desktop -l` rather than assuming a fixed name.
- **LXQt** is the simplest case: the wallpaper is controlled by a plain INI file
  (`~/.config/pcmanfm-qt/lxqt/settings.conf`), with no D-Bus involved. The command `pcmanfm-qt
  --set-wallpaper=<path> --wallpaper-mode=<mode>` applies the change without needing to restart
  the session, unlike editing the file directly.
- **MATE** uses GSettings/dconf (`gsettings set org.mate.background picture-filename <path>`),
  which also depends on an active D-Bus/dconf session to write live.

The practical common denominator: any wallpaper-change command must run inside the active
graphical session (inheriting its real `DBUS_SESSION_BUS_ADDRESS`), not as a new isolated
command — that variable's value is generated by `dbus-launch` at the moment the session starts,
and isn't automatically persisted anywhere accessible to later commands.

## Staged installation for heavy metapackages

For very heavy packages (for example, a complete security-tools metapackage), installing
everything in a single pass within a fixed time window carries a real risk: if the full install
doesn't fit in that window, the user ends up with absolutely nothing, not even the lightweight
tools. The pattern used by projects like NetHunter Rootless (`--nano`/`--minimal`/`--full`
levels) solves this by splitting the install into a fast core subset first, and only afterward
attempting the full metapackage as an optional best-effort improvement. This pattern is applied
in Kairos when installing security tools inside a Kali distro: a fast batch of core utilities
installs first, and the heavy metapackage is attempted afterward with a generous but bounded
time limit, without blocking the availability of the core batch if the metapackage doesn't
finish in time.
